## 一、设计目标

法律知识图谱的设计目标是构建一个结构化、可查询、可推理的法律知识网络，将分散的法规条文、判例数据、合同条款和法律概念以图结构组织起来，支撑以下三类应用场景：

1. **图谱查询**：用户通过关键词搜索法律实体（法规、法条、判例、法院等），系统返回匹配实体及其关联关系网络
2. **关系追溯**：沿图谱的边进行多度关系探索，例如"判例A → 引用 → 法条X → 细化 → 法条Y"
3. **知识增强**：在合同审查和法律咨询中，从图谱中检索相关的法律依据和判例参考，作为 LLM Prompt 的上下文注入

---

## 二、技术选型

本系统选择 Neo4j 图数据库作为知识图谱的存储和查询引擎，理由如下：

- **原生图存储**：法律实体之间的关系（引用、援引、变更、适用）天然是图结构，用关系型数据库需要多次 JOIN 才能完成三度关系查询，Neo4j 一条 Cypher 语句即可实现
- **Cypher 查询语言**：声明式语法使复杂的图遍历查询直观简洁，适合表达"从一个判例出发，找到它引用的所有法条，再找到引用这些法条的其他判例"这类追溯需求
- **成熟生态**：Neo4j 是图数据库领域的工业标准，社区活跃，Python 驱动完善
- **可选部署**：系统设计为 Neo4j 不可用时自动降级，不影响核心的合同审查和法律咨询功能

## 四、关系类型定义

知识图谱定义了 12 种关系类型，按语义分为三组：

### 4.1 结构关系

| 关系 | 方向 | 含义 | 示例 |
|------|------|------|------|
| CONTAINS | Law→Article / Contract→Clause | 包含条款 | 民法典 Contract→ 第584条 |
| BELONGS_TO | Article→Law / Clause→Contract | 属于 | 第584条 → 民法典 |

### 4.2 法律推理关系

| 关系 | 方向 | 含义 | 示例 |
|------|------|------|------|
| CITES | Case→Article | 判例引用法条 | 张某诉某公司案 → 劳动合同法第87条 |
| APPLIES | Article→Case | 法条适用于判例 | 民法典第584条 → 李某合同纠纷案 |
| BASED_ON | RiskPoint→Article | 风险法律依据 | 违约金过高 → 民法典第584条 |
| HAS_RISK | Clause→RiskPoint | 条款存在风险 | 违约责任条款 → 违约金过高风险点 |
| PRECEDENT_FOR | Case→Case | 作为先例 | 判例A → 判例B |
| DEFINED_IN | LegalConcept→Law | 概念定义于某法律 | "不可抗力" → 民法典 |

### 4.3 通用关联关系

| 关系 | 方向 | 含义 |
|------|------|------|
| HEARD_BY | Case→Court | 由法院审理 |
| REFERENCES | Case→Case | 互相参考 |
| RELATED_TO | 通用 | 概念关联 |
| SIMILAR_TO | Case→Case | 相似判例 |

## 五、数据构建方式

知识图谱的构建通过以下途径进行：

1. **KnowledgeExtractor（知识抽取器）**：通过 LLM 从非结构化法律文本中抽取实体和关系，定义在 `knowledge_graph/extractor.py` 中，提供 `extract_from_text()`、`extract_from_contract()`、`extract_from_case()` 和 `extract_from_law_document()` 四个方法

2. **GraphBuilder（图谱构建器）**：负责将抽取结果写入 Neo4j，定义在 `knowledge_graph/builder.py` 中，提供 `create_entity()`、`create_relationship()`、`build_from_documents()`、`build_from_case_data()` 等方法

3. **知识源文件**：原始法律文档存放于 `knowledge/` 目录，按 laws/、cases/、contracts/ 分目录组织，当前包含《民法典合同编违约责任》和《公司法公司治理》两份法律条文，以及民事判例和合同样本

4. **初始化脚本**：`scripts/init_knowledge_base.py` 负责首次部署时或知识源更新后的全量索引重建

## 六、查询方式

系统提供三层查询接口：

### 6.1 全文搜索（面向普通用户）

```
GET /api/kg/search?keyword=违约责任
→ KGQuery.search_fulltext("违约责任")
→ Neo4j 全文索引匹配
→ 返回匹配的实体列表 [Law, Article, Case, ...]
```

### 6.2 实体详情（面向法务人员）

```
点击某实体 → KGQuery.query_entity(type, id)
→ 返回实体属性 + 关联实体列表
→ 用户可沿关系链路逐层追溯
```

### 6.3 Cypher 高级查询（面向开发者）

```cypher
// 查找某个判例引用的所有法条
MATCH (c:Case {title: "张某诉某科技公司劳动争议案"})-[:CITES]->(a:Article)
RETURN c, a

// 查找与某法条相关的所有判例（二度关系）
MATCH (a:Article {article_number: "第87条"})<-[:CITES]-(c:Case)
RETURN a, c

// 查找相似判例网络
MATCH (c1:Case)-[:SIMILAR_TO]-(c2:Case)
WHERE c1.case_type = "劳动争议"
RETURN c1, c2
```

## 七、降级策略

考虑到 Neo4j 增加了部署复杂度（需要安装 Docker 或 Neo4j Desktop），系统设计为 Neo4j 不可用时自动降级：

- `KGQuery.is_available` 属性在初始化时检测 Neo4j 连接状态
- 连接失败时，知识图谱相关的前端页面和 API 端点返回"服务不可用"提示，但不影响合同审查、法律咨询等核心功能
- ChromaDB 和 Whoosh 提供替代的检索能力——虽然无法进行图关系追溯，但语义检索和关键词检索仍然可用

---

## 八、与 LLM 的协同机制

知识图谱与 LLM 的协同体现在两个环节：

1. **检索增强（RAG）**：在咨询 Agent 的混合检索中，HGQuery 的全文搜索结果与 ChromaDB 和 Whoosh 的检索结果一起作为 LLM 的上下文注入 Prompt

2. **图谱约束生成**：合同审查 Agent 在生成法律依据时，可先从图谱中检索相关法条，确保 LLM 引用的法规名称和条文编号是知识图谱中真实存在的，减少幻觉风险

---

## 九、当前数据规模与扩展方向

**当前状态**：知识库种子数据包含 2 部法律（民法典合同编 + 公司法）、2 条判例和 2 份合同样本，总计约 10 个节点和 15 条关系。Neo4j 为可选组件，当前数据主要通过 ChromaDB 和 Whoosh 提供检索。

**扩展方向**：
1. 导入公开的裁判文书数据，丰富判例节点
2. 增加行政法规和司法解释实体类型
3. 引入置信度评分，标注实体和关系的可信度
4. 支持图谱的可视化展示（在前端以力导向图呈现节点网络）
