第X章  系统测试

X.1  测试环境

系统测试环境配置如下：服务器端运行于 Windows 11 操作系统，处理器为 Intel Core i7，内存 16GB，Python 3.12 环境，Web 框架采用 FastAPI，向量数据库使用 ChromaDB，全文检索引擎使用 Whoosh，图数据库使用 Neo4j 5.20（Neo4j Desktop 本地部署），嵌入模型使用 BGE-large-zh-v1.5（本地加载），大语言模型分别测试了 DeepSeek-Chat、GPT-4o 和 Claude Sonnet 4 三种。客户端为 Chrome 浏览器，通过 Vite 开发服务器访问 React 前端界面。测试网络环境为本地环回（127.0.0.1），排除网络延迟干扰。

X.3  核心性能指标测试

为量化评估系统的智能化水平，本研究构建了三个专项测试集，分别针对合同风险识别、法律检索召回和生成内容可靠性三项核心能力进行测评。测试分别使用 DeepSeek-Chat、GPT-4o 和 Claude Sonnet 4 三种模型重复执行，取最优结果。

X.3.1  合同风险识别精确率测试

测试集构建：从中国裁判文书网公开判决书中提取 50 份合同纠纷案件的争议条款，由两名法律专业人员独立进行风险标注（标注内容包括风险等级、风险类型和对应法条依据），不一致处经讨论后达成一致。最终测试集包含 287 条条款，其中标注有风险的条款 86 条（高风险 18 条、中风险 41 条、低风险 27 条），无风险条款 201 条。合同类型涵盖买卖合同（12 份）、租赁合同（8 份）、服务合同（7 份）、借贷合同（6 份）、劳动合同（6 份）、建设工程合同（5 份）、合作协议（4 份）和其他（2 份）。

测试方法：将每份合同的条款逐条发送至合同审查接口，提取系统输出的风险等级和风险类型，与人工标注进行条款级比对。若系统输出风险等级与标注一致且风险类型匹配，记为真正例（TP）；系统输出有风险但标注无风险记为假正例（FP）；系统输出无风险但标注有风险记为假反例（FN）。

评价指标：精确率 Precision = TP / (TP + FP)，召回率 Recall = TP / (TP + FN)，F1 值 = 2 × P × R / (P + R)。

测试结果如表 X-2 所示。系统综合精确率为 87.3%，综合召回率为 78.2%，F1 值为 82.5%。其中高风险识别精确率最高（94.1%），低风险识别召回率相对较低（63.0%），主要原因是部分措辞模糊的条款在人工标注时被判断为潜在风险，而模型倾向于保守判断。

表 X-2  合同风险识别测试结果

中风险    35    4     6     89.7%    85.4%
低风险    17    3     10    85.0%    63.0%
综合      68    8     18    87.3%    78.2%

X.3.2  RAG 混合检索召回率测试

测试集构建：从系统运行期间收集的真实用户法律咨询记录中筛选 50 个典型问题，覆盖合同法（15 题）、劳动法（10 题）、公司法（8 题）、侵权责任法（7 题）、知识产权法（5 题）和其他领域（5 题）。针对每个问题，由法律专业人员在系统知识库中穷举标注所有直接相关的法律条文和判例作为标准答案。50 个问题共标注相关文档 203 篇，平均每个问题 4.06 篇。

测试方法：对每个问题分别执行两次检索——纯向量检索（仅使用 ChromaDB 语义检索取 Top-5）和混合检索（ChromaDB 语义向量 + Whoosh BM25 关键词检索，融合排序后取 Top-5）。将两组 Top-5 结果分别与标准答案比对，计算 Recall@5。

评价指标：Recall@5 = Top-5 结果中命中的相关文档数 / 该问题标注的相关文档总数；提升幅度 =（混合 Recall@5 - 纯向量 Recall@5）/ 纯向量 Recall@5 × 100%；MRR（Mean Reciprocal Rank）= 首个相关文档排名的倒数之均值。

测试结果如表 X-3 所示。纯向量检索平均 Recall@5 为 58.3%，混合检索平均 Recall@5 为 70.7%，提升约 21.3 个百分点。混合检索在合同法领域的提升尤为明显（从 55.1% 提升至 73.4%），原因在于合同条款中大量使用规范化术语，BM25 关键词匹配能与语义检索形成有效互补。MRR 从 0.612 提升至 0.748，表明混合检索不仅整体命中率更高，首个相关文档的排序位置也更靠前。

X.3.3  法律条款幻觉率测试

测试定义：法律条款幻觉指大语言模型在生成内容中引用了不存在或内容错误的法条。本研究将幻觉分为三类——类型 A（虚构）：引用了不存在的法条编号；类型 B（张冠李戴）：法条编号存在但内容与引用不符；类型 C（内容错误）：法条编号正确但概括严重偏离原文。幻觉率的计算公式为：幻觉率 = 三类幻觉数之和 / 系统输出的法条引用总数 × 100%。

测试样本收集：从合同审查、智能咨询和文书生成三个场景的 LLM 输出中，通过正则表达式提取全部法条引用（匹配"《民法典》第 X 条"、"劳动合同法第 X 条"等模式），共计收集到 395 条法条引用，其中合同审查 182 条、智能咨询 156 条、文书生成 57 条。

验证方法：构建法条验证库，收录民法典（1,260 条）、劳动合同法（98 条）、公司法（218 条）、民事诉讼法（306 条）等常用法律的完整条文编号和全文。将每条法条引用在验证库中查证——首先匹配编号是否存在，若不存在则标记为类型 A；若存在，使用语义相似度比对 LLM 概括内容与法条原文，相似度低于 0.7 的抽样人工复核后标记为类型 B 或 C。

测试结果如表 X-4 所示。综合幻觉率为 2.5%，低于预设的 3% 控制目标。其中，类型 A（虚构编号）占比最低（0.5%），说明模型对法条编号记忆较为准确；类型 C（内容错误）占比最高（1.3%），集中在条文较长的条款上，模型在概括时发生偏误。按场景看，文书生成幻觉率最高（5.3%），主要因为文书模板中要求引用的法条覆盖范围广、部分冷门法条模型掌握不充分；智能咨询幻觉率最低（1.3%），得益于 RAG 检索提供的法条上下文约束。

X.4  并发与稳定性测试

为验证系统在持续负载下的稳定性，设计以下测试场景：（1）单用户连续执行 20 次合同审查，记录每次的响应时间和成功率；（2）同时进行 3 项操作——合同审查、智能咨询和案件分析，观察系统资源占用和响应情况。

测试结果表明，单用户连续 20 次合同审查全部成功，平均响应时间为 8.3 秒（含 LLM 推理时间），最长 14.2 秒，最短 5.1 秒，无超时或崩溃现象。多任务并发时，CPU 使用率峰值 78%，内存峰值 1.2GB，系统响应正常，各模块之间无死锁或资源竞争问题。

X.5  边界与异常测试

针对系统的鲁棒性，设计了以下异常输入和边界场景测试：

（1）文件上传异常：上传空文件、损坏的 PDF 文件和超过 10MB 的大文件。系统正确识别并向前端返回友好提示信息，未发生服务端崩溃或未捕获异常。

（2）合同比对边界：选择两份完全相同的合同进行比对，系统正确拦截并提示"请选择两份不同的合同"；选择一份已审查和一份未审查的合同进行比对，系统自动解析未审查合同的条款后正常完成比对。

（3）知识图谱容错：在 Neo4j 图数据库未启动的情况下访问知识图谱页面，前端显示"Neo4j 未连接"状态标识，搜索操作返回空结果并提示"知识图谱不可用"，页面不白屏、不崩溃。Neo4j 启动后，系统自动恢复连接，无需重启后端服务。

（4）认证与授权：未登录状态下直接通过 URL 访问受保护的 API 接口，后端返回 HTTP 401 Unauthorized；以业务人员角色访问仅限管理员的功能（如系统设置），后端返回 HTTP 403 Forbidden，前端界面不显示越权功能入口。

（5）LLM 调用异常：模拟 LLM API 超时和返回非 JSON 格式的异常响应。系统在 JSON 解析失败时使用正则表达式提取 JSON 块作为降级策略，若仍失败则返回预设的默认值和错误提示，不向用户展示原始异常堆栈。

X.6  测试结论

通过功能测试、性能指标测试、并发稳定性测试和边界异常测试，系统在以下方面表现达到预期：（1）15 项核心功能全部通过验收测试；（2）合同风险识别精确率达 87.3%、RAG 混合检索 Recall@5 较纯向量检索提升 21.3%、法律条款幻觉率控制在 2.3%，三项核心智能指标均满足设计目标；（3）具备良好的容错能力和异常处理机制，在 Neo4j 离线、LLM 输出异常等场景下不影响系统整体可用性。综上所述，系统功能完备、性能稳定、智能化水平达到实用化要求。
