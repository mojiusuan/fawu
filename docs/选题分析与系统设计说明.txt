智能法务系统 —— 选题分析、需求分析与系统设计


一、对选题的分析

这道题的三个关键词——大语言模型、智能体技术、法务系统——界定了课题的核心命题：不是单纯做一个法律信息展示网站，而是要让 AI 真正参与法律业务的处理过程。

我先拆解了题目要求的三层含义。第一层是"集成合同管理、法律咨询、案件分析等功能模块"——这意味着系统不能是单功能的，起码要覆盖法务日常的三个核心场景。第二层是"运用生成式 AI 技术实现法律文档的智能处理"——AI 在这里不是锦上添花的辅助，而是业务的核心驱动力，审查、分析、生成都要靠 LLM 来完成。第三层是"自动化的业务流程"——不是人操作一步 AI 执行一步，而是 Agent 能自主规划任务步骤、调用工具、完成多步流程。

基于这个理解，我确定了设计的核心原则：AI 不是系统的功能之一，而是系统的基础能力；Agent 不是单个智能体，而是协调多个专业智能体的调度框架。


二、法律业务需求分析

我从三个维度分析了法务业务的真实需求。

第一个维度：用户角色分化。法律服务的用户不是一个整体——普通民众需要低门槛的即时咨询，专业律师需要高效率的审查工具，系统管理员需要可控的运维能力，审计人员需要可追溯的操作记录。这意味着系统必须做角色化设计——不是一套功能给所有人用，而是不同角色看到不同界面、使用不同功能。

第二个维度：核心业务场景。法务人员的日常工作中，重复性最高的三件事是：合同审查、法律检索和案件分析。合同审查——拿到一份合同，逐条看有没有法律风险，引用法律依据，给出修改建议。这个过程高度结构化，非常适合 LLM 来做。法律检索——为某个法律问题查找相关法条和判例，这需要检索能力而非纯粹的生成能力。案件分析——从案情描述中提取关键要素，匹配相似判例，评估风险——需要 LLM 的理解和推理能力。

第三个维度：合规与安全。法律服务有严格的监管要求。AI 生成的内容必须标注来源，所有决策过程必须可追溯。这意味着系统需要一个不可篡改的审计日志机制，记录每次 LLM 调用的完整上下文。

这三层分析直接驱动了后续的设计决策：角色化→四类用户的权限体系；业务场景→六个 Agent 的功能分工；合规要求→追加写入的审计日志系统。


三、系统技术架构设计

基于需求分析，我设计了四层架构。

表示层是 Web 前端。采用零依赖的单页应用——一个 HTML、一个 CSS、一个 JavaScript 文件，通过 JWT 令牌与后端通信。设计决策是刻意不引入前端框架：一是部署简单，FastAPI 直接托管静态文件；二是两千行 JS 对单体应用足够，引入 React 反而过度工程。

接口层是 FastAPI 应用，以 APIRouter 机制组织了十二组 RESTful 端点。设计决策是每个功能模块独立路由，模块之间通过 Python 的 import 机制而非 HTTP 调用进行通信——同进程调用延迟为零，不需要服务间认证。

业务逻辑层是系统的核心。每个模块内部遵循"路由→服务→代理"三层结构——路由负责参数校验和响应格式化，服务负责业务编排和数据持久化，代理负责与 LLM 和外部资源的交互。这种结构的好处是关注点分离：换 LLM 提供商只改代理层，加缓存只改服务层，加参数验证只改路由层。

基础设施层提供跨模块的通用能力。核心是 LLMClient——一个统一封装了 DeepSeek、Claude、OpenAI 三家 API 的调用网关，上层 Agent 不关心底层到底调的是哪家模型。此外还有混合检索引擎（ChromaDB 语义检索 + Whoosh 关键词检索）、知识图谱（Neo4j）、审计日志和 JWT 认证。

数据存储设计遵循"按数据特性选存储引擎"的原则。业务数据（合同、用户、案件）用 JSON 文件——数据量小、结构灵活、便于备份和迁移。法律知识检索用 ChromaDB 向量库——法律概念的语义匹配需要向量相似度计算，关系型数据库做不了。全文精确匹配用 Whoosh——法条编号的精确查找需要 BM25 算法，向量检索不够准。知识图谱用 Neo4j 图数据库——法律实体间的引用、援引、变更关系天然是图结构，用关系型数据库需要多次 JOIN，用图数据库一条 Cypher 查询就能完成三度关系的追溯。


四、Agent 架构设计

这是整个系统最核心的设计决策。

首先要回答一个问题：为什么需要 Agent？如果每个功能都是"用户输入→构造 Prompt→调用 LLM→返回结果"的单次调用链，整个系统就是六个独立的 Prompt 模板加上六个 API 端点。这确实能工作，但天花板很低——你无法处理"先审查合同，如果发现高风险条款，再查相关判例，最后生成法律意见"这种多步任务。

Agent 的本质是把 LLM 从"回答问题的人"升级为"调度任务的指挥官"。指挥官不需要亲自审合同、查法条、写报告——他只需要判断"这个任务应该分给谁"，然后分下去。

基于这个理解，我选择了 Supervisor 模式。整个 Agent 系统分三层。决策层只有一个 Supervisor，职责极其单一：接收用户输入，调用 LLM 做一次意图识别（temperature=0.0，追求确定性），输出一个 JSON——{"agent": "contract_agent"}。然后由条件路由函数把这个任务送到对应的专业 Agent。执行层是四个专业 Agent——合同 Agent、咨询 Agent、RPA Agent、图谱 Agent——每个只负责自己领域的任务。能力层是六个工具函数，供 Agent 在执行过程中调用。

为什么是 Supervisor 而不是多 Agent 直接协作？因为当前系统的任务类型是互斥的——一个用户请求要么是审查合同，要么是法律咨询，很少需要两个 Agent 同时处理。Supervisor 模式在这种场景下效率最高——一次 LLM 调用完成路由，专业 Agent 直接执行，没有多余开销。多 Agent 协作更适合复杂任务——比如"先检索最新法规，再基于新法规审查合同"——这类场景是未来的扩展方向，当前架构已经留好了扩展点。

Agent 之间的信息传递靠 AgentState。这是一个 TypedDict，七个字段在所有节点之间共享——用户输入、任务类型、下一节点、对话历史、中间上下文、最终结果、完成标志。Supervisor 往里面写 task_type，执行 Agent 读这个字段就知道自己要做什么。执行 Agent 写好 result 和 finished=True，图引擎检测到 finished 就终止执行。节点之间完全解耦——加一个新 Agent 不影响任何现有节点。

容灾设计是 Agent 系统的底线保障。Supervisor 的 LLM 调用偶尔会返回格式不正确的 JSON——缺个引号、多个换行，导致解析失败。如果这时候系统报错，用户的请求就掉地上了。所以设计了双保险：主路径是 LLM 意图识别，备用路径是关键词匹配。检测到"合同/审查/条款"→contract_agent，"图谱/案例关系"→kg_agent，其他→consultation_agent。宁可路由不够精准，不能让请求丢失。

为什么编排器和实际 Agent 类是分离的？这是一个刻意的架构预留。编排器的四个 Agent 节点当前是占位实现——只返回确认文本，不执行真实业务。真实的业务逻辑在 ContractAgent、ConsultationAgent、RPAAgent、KGQuery 等类中，通过 API 路由直接调用。这两条路径并行存在：直接路径用于当前的高频单步任务（用户明确点击"合同审查"按钮），编排路径用于未来的多步协作任务（用户在一个对话框里说"先审合同，再查判例，再写意见书"）。两条路径不是冗余——它们分别服务于简单场景和复杂场景。


五、关键设计决策总结

整个系统设计过程中，有几个反复权衡后做出的关键决策。

一是 JSON 文件 vs 关系型数据库。对于四用户、十合同、五条咨询记录的量级，JSON 文件的读写延迟在毫秒级，引入 MySQL 是过度设计。数据量增长到千级以上时再迁移，JSON 到 SQL 的迁移成本远低于提前引入数据库的维护成本。

二是单 Agent 执行 vs 多 Agent 协作。当前阶段，合同审查、法律咨询、文档提取是独立任务，不需要协作。Supervisor 的单次路由足够。多 Agent 协作的框架已经搭好——把节点间的 END 改回 supervisor 就能形成循环链路——但当前阶段不应该为了架构而架构。

三是知识图谱可选 vs 必选。Neo4j 增加了部署复杂度（需要安装 Docker 或 Neo4j Desktop），所以在连接失败时系统自动降级——知识图谱功能不可用，但合同审查和法律咨询不受影响。这个设计决策的原则是：增强功能可以降级，核心功能不能中断。

四是 RAG 双通道检索。法律场景同时需要语义理解和精确匹配——"解雇"和"解除劳动合同"在语义上高度相关，这是向量检索的优势；"劳动合同法第三十九条"要求精确查找，这是关键词检索的优势。单独用任何一种都覆盖不全，混合检索是法律场景的最优解。
