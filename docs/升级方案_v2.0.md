# 智能法务系统 v2.0 升级方案

## 概述

在 v1.0 现有能力（合同管理、智能咨询、知识图谱、RPA 文档提取、合规审计）基础上，升级为**业务能力齐全的法务原型系统**，覆盖"案前评估 → 证据准备 → 费用测算 → 文书生成 → 判例参考 → 人工兜底"完整业务闭环。

### 现有基础

| 能力域 | v1.0 已有 | 可复用 |
|---|---|---|
| RAG 检索引擎 | ChromaDB + Whoosh 混合检索，支持法律/判例/合同三源 | 全部复用 |
| 知识图谱 | Neo4j 8类实体 + 12类关系 + 全文搜索 | 全部复用 |
| LLM 调用 | DeepSeek/Claude/GPT-4o 三供应商统一封装 | 全部复用 |
| 合同管理 | 上传/RPA提取/审查/比对/生成 + docx 导出 | 审查引擎复用 |
| 认证授权 | JWT + RBAC 四角色（admin/legal/business/auditor） | 全部复用 |
| 合规审计 | 全链路日志 + 决策追溯 + 审计报告 | 全部复用 |
| 前端框架 | web/ SPA（HTML+CSS+JS+GSAP 动画）+ web_ui/ Streamlit | 页面框架复用 |
| 嵌入模型 | 本地 bge-large-zh-v1.5（免费离线） | 全部复用 |

### 服务模块设计原则

1. **不引入新框架/新数据库**——继续使用 FastAPI + JSON 文件存储 + ChromaDB + Neo4j
2. **每个模块独立 service 文件**——避免耦合，可单独测试、单独上线
3. **复用现有 LLM/RAG/KG 引擎**——新模块的核心智能能力全部基于已有引擎
4. **所有计算逻辑必须有明确的法律依据来源**——计算器内置公式参数标注法条出处

## 数据模型设计

### 新增 JSON 存储文件

```
data/
├── case_profiles.json       # 案件档案
├── case_analyses.json       # 案情分析记录
├── evidence_guides.json     # 证据指引配置（案由→证据清单映射）
├── doc_templates.json       # 文书模板元数据
├── fee_rules.json           # 诉讼费计算规则
├── compensation_rules.json  # 赔偿计算规则
├── limitation_rules.json    # 诉讼时效规则
└── topic_libraries.json     # 法规专题包配置
```

### 核心数据模型

```python
# === 案件档案 ===
class CaseProfile:
    case_id: str                    # UUID
    user_id: str
    case_name: str                  # 用户命名的案件名称
    case_type: str                  # 案由枚举: labor/loan/injury/marriage/consumer/property/contract/other
    status: str                     # 状态: assessing/negotiating/litigating/closed
    parties: dict                   # {"plaintiff": {...}, "defendant": {...}}
    facts: str                      # 案情描述（原始）
    structured_facts: dict          # 结构化案情要素
    created_at: str
    updated_at: str

# === 案情分析报告 ===
class CaseAnalysis:
    analysis_id: str
    case_id: str
    user_id: str
    structured_facts: dict          # 提取的结构化要素
    legal_basis: list[dict]         # 适用法律依据 [{law, article, relevance}]
    similar_cases: list[dict]       # 相似判例 [{case_number, title, similarity, key_points}]
    risk_assessment: dict           # 风险评估 {level, factors[], suggestions[]}
    fee_estimate: dict              # 费用估算（可选嵌入）
    evidence_checklist: list[dict]  # 证据清单
    limitation_check: dict          # 时效检查结果
    generated_at: str

# === 证据指引 ===
class EvidenceGuide:
    case_type: str                  # 案由
    required_evidence: list[dict]   # 必要证据 [{name, description, format, sample}]
    optional_evidence: list[dict]   # 补充证据
    preservation_tips: list[str]    # 证据保全建议
    collection_methods: list[str]   # 取证方法指引

# === 诉讼费用 ===
class FeeEstimate:
    case_type: str
    claim_amount: float             # 诉讼标的额
    court_fee: float                # 案件受理费
    preservation_fee: float         # 保全费
    execution_fee: float            # 执行费
    total: float
    fee_breakdown: list[dict]       # 分项说明
    reduction_note: str             # 减免说明（如适用）

# === 赔偿估算 ===
class CompensationEstimate:
    scenario_type: str              # labor/injury/loan/consumer
    items: list[dict]               # [{name, amount, basis, formula}]
    total_min: float
    total_max: float
    notes: list[str]

# === 文书模板 ===
class DocumentTemplate:
    template_id: str
    category: str                   # indictment/application/defense/petition/other
    title: str                      # 模板名称（如"民事起诉状"）
    description: str
    applicable_scenarios: list[str]
    required_fields: list[dict]     # 需填写的字段 [{key, label, type, options?, required?}]
    template_content: str           # 模板正文（含占位符 {{field_name}}）
    sample_content: str             # 填写示例
    legal_basis: list[str]          # 法律依据
    download_count: int
    created_at: str
```

## 关键技术决策

### 1. 判例匹配策略

```
用户输入案情描述
    │
    ├─→ RAG 语义检索 (ChromaDB) → Top-10 候选判例
    ├─→ KG 案由关联检索 (Neo4j) → 同案由 + 同法条判例
    │
    └─→ LLM 精排 (rerank)
         ├─ 输入: 案情要素 + 10 候选判例摘要
         ├─ 输出: Top 3-5 最相似判例 + 相似度说明 + 关键差异
         └─ 格式化: 案号 / 法院 / 裁判日期 / 争议焦点 / 判决结果 / 相似理由
```

### 2. 案情分析 LLM Prompt 策略

```
Step 1 — 要素提取
  输入: 用户自然语言案情描述
  输出: 结构化 JSON（案由、当事人关系、时间线、争议标的、关键事实）
  约束: 不编造用户未提及的事实，缺失字段标记为 "未知"

Step 2 — 法律适用分析
  输入: 结构化要素 + RAG 检索到的相关法条
  输出: 适用法律条款 + 适用理由引用案情要素

Step 3 — 风险评估
  输入: 结构化要素 + 适用法条 + 相似判例结果
  输出: 风险等级 + 风险因素列表 + 法律依据 + 应对建议
```

### 3. 费用计算规则

诉讼费严格按《诉讼费用交纳办法》（国务院令第481号）：
- 财产案件：按标的额分段累计
- 非财产案件：固定金额 + 分段
- 保全费：按保全金额比例
- 执行费：按执行标的额分段

赔偿计算按具体场景分别建模（N+1 补偿、人身损害赔偿项目累加、借贷本息 LPR 4 倍上限等）。

### 4. 文书组装实现方式

不依赖 LLM（避免幻觉），采用**模板引擎模式**：
- 模板存储为带 `{{占位符}}` 的 Markdown
- 用户填写的结构化数据通过 Jinja2 填入模板
- 生成 docx 使用 python-docx（已有），生成 PDF 使用 WeasyPrint/playwright

### 5. PDF 导出选型

推荐 **Playwright**（项目已依赖）从 HTML 渲染 PDF：
- 复用现有 CSS 样式
- 支持中文字体
- 方案：HTML 模板 → Playwright headless → PDF 文件

### 6. 新增 Python 依赖

```
jinja2          # 文书模板渲染（通常已安装）
reportlab       # PDF 备选方案（纯 Python，无外部依赖）
```

## 风险与约束

| 风险 | 缓解措施 |
|---|---|
| LLM 幻觉导致分析不准确 | 分析报告强制标注"AI生成仅供参考"；法条引用必须通过 RAG 检索而非 LLM 生成 |
| 相似判例不足（知识库数据少） | 首批手工精选 20+ 高频案由判例；后续可爬取公开裁判文书 |
| 赔偿计算覆盖场景不全 | 先支持 4 个高频场景（劳动/借贷/人身损害/消费），后续按需扩展 |
| 用户高期望与实际 AI 能力差距 | 所有页面显著位置展示免责声明；提供明确的人工转接路径 |
| 判例推荐中的时效性问题 | 标注裁判日期，超过 5 年的判例提示"法律环境可能发生变化" |

## 验收标准

### 第一階段验收
- [ ] 用户可选择案由，填写案情要素，生成完整分析报告
- [ ] 分析报告包含：案情摘要 + 适用法律 + 相似判例(3-5) + 证据清单 + 时效检查 + 费用估算 + 风险评估
- [ ] 判例匹配结果包含案号、法院、裁判日期、争议焦点、相似度说明
- [ ] 诉讼费计算器对 5 组测试金额计算结果与《诉讼费用交纳办法》一致
- [ ] 仲裁时效/诉讼时效计算正确，含边界情况（刚到期、已过期）

### 第二階段验收
- [ ] 文书模板库可浏览、搜索、分类筛选
- [ ] 组装向导可填写字段 → 生成完整文书 → 下载 docx
- [ ] 案件中心可创建/查看/更新/删除案件档案
- [ ] 案件卡片正确关联分析报告、生成文书

### 第三階段验收
- [ ] 案件分析报告可导出为排版正确的 PDF
- [ ] 法规专题库可按场景检索到相关法条+解释+案例
- [ ] 人工转接表单可提交并返回状态
